# Naples Chess Club — website

Static site. No build step, no dependencies, no framework. Edit the files, push, done.

```
index.html              the home page
404.html                not-found page
robots.txt              crawler rules + sitemap pointer
sitemap.xml             GENERATED by build-blog.js — don't edit by hand
feed.xml                GENERATED RSS feed
CNAME                   custom domain for GitHub Pages
.nojekyll               stops GitHub mangling files that begin with _
set-domain.sh           rewrites every URL when the domain changes
build-blog.js           turns Markdown posts into static HTML
backend/
  Code.gs               the RSVP backend (Google Apps Script)
  SETUP.md              how to deploy it, about 10 minutes
blog/
  _posts/*.md           YOU EDIT THESE — one Markdown file per post
  index.html            GENERATED blog listing
  <slug>/index.html     GENERATED post pages
assets/
  logo.svg              the club crest (vector, 34 KB → 10 KB gzipped)
  css/styles.css
  js/main.js
  img/                  hero at 3 widths, WebP + JPEG, OG + per-post images
```

**First load on a phone: ~38 KB gzipped.** That is the whole page, crest and hero photo included.

Anything marked GENERATED is overwritten by `node build-blog.js`. Edit the
Markdown, not the HTML.

## Run it locally

```bash
python -m http.server 4173
```

Then open <http://localhost:4173>.

Use a server, not `file://` — the absolute paths (`/assets/...`) and the
structured data both need a real origin to behave the way they will in production.

---

## Set your domain

Everything SEO-related hardcodes the domain, because canonical URLs, Open Graph
images and structured data all require absolute URLs. One command updates them all:

```bash
./set-domain.sh yourdomain.com
```

Run this **before** the first deploy. Re-run it any time the domain changes.

## RSVPs and the mailing list

The RSVP form posts to a Google Apps Script web app, which appends a row to a
Google Sheet you own and emails the guest a confirmation. There is no server and
no cost.

**It is not live until you deploy it.** Follow [backend/SETUP.md](backend/SETUP.md),
then paste the resulting URL into `assets/js/main.js`:

```js
var RSVP_ENDPOINT = '';   // line 15
```

Until that is filled in, the form hides itself and the page shows "text us
instead", so a half-finished setup never looks broken to a visitor.

The sheet is your mailing list. Export it as CSV whenever you want to send
something.

## Deploy to GitHub Pages (free)

1. Create a repo on GitHub — public, no README (you already have one).

2. From this folder:

```bash
git init -b main
git add -A
git commit -m "Naples Chess Club website"
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPO.git
git push -u origin main
```

3. In the repo: **Settings → Pages → Source: Deploy from a branch**,
   branch `main`, folder `/ (root)`. Save.

4. Still on that page, put your domain in **Custom domain** and save.
   Tick **Enforce HTTPS** once it becomes available (can take ~15 minutes
   while GitHub issues the certificate).

## Point the domain at GitHub Pages

At your domain registrar, for the **apex** domain (`yourdomain.com`), create four
`A` records pointing at GitHub:

```
185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153
```

And one `CNAME` record for `www`:

```
www  ->  YOUR-USERNAME.github.io
```

DNS usually propagates within an hour, occasionally up to 24. Verify with:

```bash
dig +short yourdomain.com
```

## After it's live

- **Google Search Console** — <https://search.google.com/search-console>.
  Add the property, verify by DNS TXT record, then submit `sitemap.xml`.
  This is the single highest-value thing you can do for search visibility.
- **Google Business Profile** — <https://business.google.com>. A local club
  with a real address and fixed weekly hours ranks far better in Maps and
  local search with a claimed profile. Use the exact same name, address and
  phone number as the site, character for character.
- **Bing Webmaster Tools** — can import directly from Search Console. Also
  feeds some AI answer engines.

## Writing a blog post

Blog posts are the cheapest SEO you have. Each one is a new page that can rank
for its own search terms, and search engines reward a site that keeps changing.

**1. Create a Markdown file** in `blog/_posts/`, named `YYYY-MM-DD-some-slug.md`:

```markdown
---
title: How Our Club Ran Its First Tournament
description: One sentence that shows up in Google results. Keep it under 160 characters.
date: 2026-11-05
updated: 2026-11-12
role: pillar
keywords: naples chess tournament, chess tournament florida
related: chess-in-naples-florida, does-chess-make-you-smarter
image: /assets/img/og-image.jpg
imageAlt: Describe the picture for screen readers
---

Your opening paragraph. Just write normally.

## Key takeaways

- These become the highlighted summary box at the top
- AI search engines quote this block, so make each line stand alone

## A normal heading

Body text. **Bold**, *italic*, and [a link](https://example.com).

> A pull quote.

## Frequently asked questions

### A question someone would actually type?

The answer. Every question here is also emitted as FAQPage structured data,
which is what wins the answer box in Google.

## Sources

1. Author. "Title." *Journal*, year. [Link](https://example.com)
```

`title`, `description` and `date` are required. Everything else is optional.

### The conventions worth knowing

| What you write | What you get |
| --- | --- |
| `## Key takeaways` | Highlighted summary box, marked up as `speakable` for voice and AI |
| `## Frequently asked questions` with `###` questions | Accordion plus FAQPage schema |
| `## Sources` | Citation block at the end |
| `:::checklist` ... `:::` | Printable checklist card with tick boxes |
| `role: pillar \| resource \| research` | Badge on the card, and the schema type |
| `related: slug-one, slug-two` | "Keep reading" cards at the end |
| Three or more `##` headings | Table of contents, generated automatically |
| A markdown table | A styled table |

Everything else is ordinary Markdown.

### House style

**No em dashes.** They read as machine-written. Use a comma, a full stop, or
restructure the sentence. The build does not enforce this, so it is on you.

**2. Build:**

```bash
node build-blog.js
```

That writes the post page, refreshes the blog index, and regenerates
`sitemap.xml` and `feed.xml` so Google finds the new post.

**3. Commit and push.** GitHub Pages publishes within a minute or so.

### The cluster

The three existing posts form a topic cluster, which is how a small site
out-ranks bigger ones on specific terms:

- **Pillar** (`chess-in-naples-florida`) is the broad hub targeting the head term.
- **Resource** (`chess-opening-principles-checklist`) is the link magnet. It is the page other sites and forums have a reason to link to.
- **Research** (`does-chess-make-you-smarter`) is the authority piece. It cites real studies, including the ones that undercut the popular claim, which is exactly why it is credible.

All three link to each other, in the body text and through the "Keep reading"
cards. When you add a post, point its `related` at the pillar and add it to the
pillar's `related` in return. The build warns you if a `related` slug does not exist.

### What makes a post worth writing

Write for a real search someone would type. "Where to play chess in Naples" is a
real search. "Our thoughts on chess" is not. Local, specific and genuinely useful
beats clever every time, and one good post a month comfortably beats four thin ones.

## Editing content

Almost everything lives in `index.html` as plain readable HTML.

**If you change the meeting time, place, or phone number, update it in all of these:**

1. The visible HTML (hero, essentials cards, Find Us, footer)
2. The `<meta name="description">` near the top
3. The Open Graph description
4. The `application/ld+json` block at the very bottom — `openingHoursSpecification`,
   the `Event` `eventSchedule`, and the `address`/`geo` fields

Search engines read 4 as authoritative for rich results, so it drifting out of
sync with 1 is the main way a site like this starts showing wrong hours in Google.

The "next chess night" date in the gold pill computes itself from the current
date in `assets/js/main.js` — it always shows the upcoming Wednesday in Eastern
time, so it stays correct without anyone touching it.
